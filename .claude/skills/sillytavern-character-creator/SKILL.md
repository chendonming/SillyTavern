# SillyTavern 角色卡生成技能 v2

## 核心原则：用户是小白

⚠️ **重要：你面对的用户很可能完全不懂角色卡**。
- 用户不知道每个字段到底是干什么的
- 用户不知道 SillyTavern 的能力边界在哪里
- 用户不知道什么是世界书、人设、深度提示、talkativeness
- **你的职责不是"按用户说的做"，而是先主动介绍有哪些能力，再帮用户选**

> 错误示范：直接问 "角色名是什么？性格是什么？" → 用户不知道这些字段有什么效果
> 正确做法：先解释 "角色卡有 description/personality/scenario/first_mes 四个核心字段，分别控制...你想怎么填？我建议你..."

---

## 概述

根据用户需求，生成一整套 SillyTavern 角色资源：

| 产物 | 格式 | 说明 |
|---|---|---|
| 角色卡 | JSON（V2 spec） | 含内嵌世界书（character_book），可直接导入 SillyTavern |
| 独立世界书 | JSON（SillyTavern world info） | 可选，当内嵌世界书条目 > 5 时也生成一份独立的 |
| 用户人设（Persona） | JSON（backup/restore 格式） | 与角色卡人设匹配的 {{user}} 定义 |

所有文件存入 `example/角色名/` 目录。

## 字段完全指南（逐个解释）

### 1. 角色卡顶层（V2 外壳）

```json
{
  "spec": "chara_card_v2",
  "spec_version": "2.0",
  "data": { ... }
}
```

- **`spec`** — 固定写 `"chara_card_v2"`，告诉 SillyTavern 这是 V2 版本的角色卡
- **`spec_version`** — 固定写 `"2.0"`
- **`data`** — 角色卡的全部内容都在这个对象里面

### 2. data 核心字段（逐一解释）

#### `name`（必填）—— 角色名字
- 就是 AI 扮演的角色叫什么
- 中文名优先（如"苏晚晴"），也可以用英文、日文
- **影响**：AI 在对话中会用这个名字自称，并且聊天记录里角色说的话前面会显示这个名字

#### `description`（必填）—— 角色描述
- **这是 AI 理解"角色是谁"的最核心输入之一**
- 写什么：一段完整的中文描述，包含外貌（身高、发型、体型、肤色、特殊特征）+ 身份（职业、年龄）+ 气质概述
- **高级技巧**：可以把外貌描写自然融入场景，而不是生硬罗列。例如：
  - ❌ "身高172cm，F罩杯，黑长直"（生硬）
  - ✅ "她站在花丛中，一头如瀑的黑发垂至腰际，高挑修长的身姿在阳光下投下优雅的剪影"（生动）

#### `personality`（必填）—— 性格描述
- **这是控制角色"怎么说话、怎么做事"的核心字段**
- 写什么：性格特征（温柔、傲娇、腹黑...）、社交方式（被动/主动）、价值观、情绪特点
- 必须包含 `{{char}}` 引用角色名（AI 会自动替换）
- **NSFW 扩展用法**：对于性爱角色，这里要写角色在性事中的表现（是否害羞、敏感带、反应模式等）
- 示例：
  ```
  {{char}}性格温柔内向，不善拒绝别人。被夸奖时会脸红，手足无措地转移话题。
  ```

#### `scenario`（必填）—— 场景/背景设定
- **定义"角色和你在什么场景中"**
- 写的内容包括：
  - `{{user}}` 和 `{{char}}` 的关系（邻居？情侣？陌生人？师徒？主仆？）
  - 故事发生的场景（学校的教室？异世界的酒馆？未来的飞船？）
  - 当前的状况（刚认识？交往中？共同冒险？）
- 这个字段控制 AI 理解"你们现在在哪里、什么状态"

#### `first_mes`（必填）—— 开场白
- **角色对你说的第一句话，也是你对角色卡的第一印象**
- 写法：动作描写 + 对话内容
- 格式示例：
  ```
  （轻轻推开门，探进半个身子，对你露出温柔的微笑）你来了啊...我等你好久了。
  ```
- **重要性**：这段文字直接决定了角色说话的"调性"——是温柔、冷淡、热情、还是害羞

#### `mes_example`（必填）—— 示例对话
- ⭐ **最重要的字段！AI 学习角色说话方式的核心教材**
- 格式：`<START>` 和 `<END>` 包裹的一段段对话
- 使用 `{{user}}` 代表用户，`{{char}}` 代表角色
- **为什么它最重要**：
  - system_prompt 里写一万句"要温柔"不如一段示例对话来得有用
  - AI 会从示例中学到：语气词（"嗯..."、"那个..."）、句尾风格、接话方式、对特定话题的反应
  - 示例对话就是"活教材"，AI 会模仿示例中的说话方式
- **建议覆盖的场景**：
  - 日常聊天（建立 baseline 语气）
  - 调情/暧昧（展示角色对 {{user}} 的态度）
  - 意见不合（展示角色如何处理冲突）
  - 亲密场景（NSFW 角色必须要有）
- NSFW 示例至少包含：前戏（亲吻/爱抚）→ 正戏（插入/体感）→ 高潮反应 → 事后温存

示例：
```
<START>
{{user}}: 你今天心情不错啊。
{{char}}: （转头看向你，眼尾弯了弯）因为...你在呀。
<END>
<START>
{{user}}: 我可以吻你吗？
{{char}}: （睫毛轻轻颤了颤，缓缓闭上眼睛，声音细得像蚊蚋）...嗯。
<END>
```

#### `creator_notes`（必填）—— 创作者笔记
- **给 AI 看的额外说明**，不影响对话，但 AI 可以读到
- 放什么：角色的额外背景、互动原则、特殊设定
- **与 system_prompt 的区别**：creator_notes 更像是"幕后注释"，system_prompt 是"直接指令"

#### `system_prompt`（必填）—— 系统提示词
- **直接指令 AI 如何扮演角色的核心指令**，会放在 prompt 的最前面
- 这里写的所有内容 AI 都会"绝对遵从"
- 要写什么：
  1. 角色设定概要（一句话总结）
  2. 外貌要点
  3. 性格要点
  4. 语言风格要求
  5. **必写规则**：不能替用户行动、不能替用户说话
  6. NSFW 时：性爱描写要求、敏感带、禁写清单

#### `post_history_instructions`（必填）—— 历史后指令
- **放在聊天历史最末尾的特殊指令**
- 与 `system_prompt` 的区别：
  - `system_prompt` 在 prompt 最前面 → 控制整体行为
  - `post_history_instructions` 在 prompt 最后面 → 控制"接下来怎么做"
- **高级用法**：用来放"当前场景"或"剧情推进"指令，比如：
  - "现在是深夜，角色已经困了"
  - "故事达到高潮，描写要更加激烈"
- 在 SillyTavern 的设置里，这个字段也可以当成 "jailbreak prompt"（越狱提示词）来用

#### `alternate_greetings`（必填，数组）—— 备选开场白
- **多个不同的开场白**，用户可以在角色编辑界面切换
- 至少写 3 个，场景不同（比如：偶遇、上门做客、深夜邀约等）
- 用户在导入角色后在聊天界面可以随时切换开场白，开始新对话

#### `tags`（必填，数组）—— 标签
- 搜索和分类用的关键词
- 中英文均可，如 `["温柔", "御姐", "NSFW", "F罩杯"]`
- 不影响 AI 行为，只影响角色列表的搜索

#### `creator`（必填）—— 创作者
- 你的名字，可以写 `"Claude"`、网名或者留空

#### `character_version`（必填）—— 版本号
- 从 `"1.0"` 开始，后续修改变大版本号
- 不影响 AI 行为，只是一个记录

### 3. extensions 字段（SillyTavern 的内置扩展）

`extensions` 是角色卡里**功能最丰富但用户最不懂的部分**。必须主动解释每个选项的含义并推荐设置：

```json
"extensions": {
  "talkativeness": 0.5,
  "fav": false,
  "world": "关联的世界书名",
  "depth_prompt": {
    "prompt": "在特定深度注入的额外指令",
    "depth": 4,
    "role": "system"
  },
  "regex_scripts": [],
  "display_name": "角色显示名"
}
```

#### `talkativeness`（0~1 的数值）
- **这个字段控制角色在群聊中的"说话概率"和单人聊天中的"话多程度"**
- 值越大，角色越倾向于说话（回复越长/群聊中越主动发言）
- 建议值：
  | 数值 | 含义 | 适用类型 |
  |---|---|---|
  | 0.1~0.3 | 非常安静 | 被动型、害羞型、沉默寡言 |
  | 0.4~0.6 | 适中（默认0.5） | 普通角色 |
  | 0.7~0.9 | 话多 | 活泼型、话痨、元气系 |
  | 1.0 | 极端话多 | 几乎每次都抢话 |

#### `fav`（true/false）
- 是否标记为"收藏角色"
- 不影响 AI 行为，只影响收藏列表

#### `world`（字符串）
- 关联的"世界书/世界观"文件名
- **如果不填这个，世界书不会自动加载！**
- 值应该是世界书 JSON 文件的文件名（不含 `.json` 后缀）

#### `depth_prompt`（对象）—— ⭐ 高级功能
- **在对话历史的特定"深度"插入额外指令**
- 这是什么意思？—— 普通 system_prompt 只在开头生效。但随着对话变长，旧消息被挤出上下文窗口，system_prompt 的效果会减弱。depth_prompt 会在对话的特定位置（比如第 4 条消息处）重新注入指令，让 AI "想起来该怎么办"
- 三个子字段：
  - **`prompt`**：要注入的文字（可以空着，就是禁用了）
  - **`depth`**：在第几条消息处注入（默认 4）。越小越靠前
  - **`role`**：以什么角色说的话的形式注入
    - `"system"` — 系统指令（最常用）
    - `"user"` — 假装是用户说的
    - `"assistant"` — 假装是 AI 自己说的
- **什么时候用这个？**
  - 当角色的关键行为指令需要在对话中段重复强调时
  - 当需要"过了一段时间后角色态度变软/变硬"时
  - 对于 NSFW 角色，可以用 depth_prompt 在适当深度重新注入性描写指引

#### `regex_scripts`（数组）—— ⭐ 高级功能
- **角色专属的文字替换规则**
- 比如：角色说话喜欢夹杂英文 → 写一个 regex 自动给某些词加英文
- 比较复杂，通常用户不会用到，但可以提一下

#### `display_name`（字符串）
- 在聊天界面显示的 **别名**
- 比如角色本体叫"林月"，但在特定场合显示为"月儿酱"
- 不填则显示 `name` 字段

## 工作流程

### Phase 1：先给用户科普 → 再采集需求

这是最重要的步骤。**不要直接问"你要什么角色"，而是先告诉用户能做到什么程度**。

你应该这样引导用户：

**Step 1.1 — 告诉用户 SillyTavern 角色卡能定义到什么程度：**
> "SillyTavern 的角色卡非常强大，我来给你介绍一下它能做些什么："
>
> 1. **基础形象**：角色的名字、外貌、年龄、职业 — 这是最基本的
> 2. **性格定义**：详细的性格描述，AI 会根据这个来扮演性格
> 3. **场景设定**：你和角色之间是什么关系？在什么场景相遇？
> 4. **说话风格**：通过"示例对话"教 AI 角色的说话方式 — 这是最重要的
> 5. **世界观背景**：可以内置"世界书"，当聊天中提到某些关键词时自动补充相关的背景知识
> 6. **NSFW 内容**：如果需要成人向内容，我可以在角色卡里加入性爱描写指引
> 7. **深度提示**：可以在聊到特定位置时重新注入额外指令，保持角色一致性
> 8. **用户人设**：还可以生成一个"你"的人设卡，让 AI 更了解 {{user}} 的形象

**Step 1.2 — 逐项询问（每个问题都解释一下这个字段是干嘛的）：**

```
1. 角色名字叫什么？（中文优先）
2. 是什么类型的角色？（温柔女友？傲娇青梅？霸道总裁？猫娘？...）
3. 外貌有哪些特征？（身高、体型、发型、肤色、特殊特征）
4. 性格关键词有哪些？（3-6个词就够了）
5. 你和角色的关系是什么？（情侣？邻居？陌生人？主仆？）
6. 故事发生在什么场景中？（现代校园？异世界冒险？科幻未来？）
7. 说话风格是怎样的？（轻声细语？毒舌？冷淡？元气满满？）
8. 要不要 NSFW 内容？（如果你想要成人向内容，我会加入性爱描写指引）
9. 有没有特别的背景设定？（比如角色有什么秘密、特殊能力、过去的经历）
```

每一问间隔等待用户回复，不要一次性全问完。

### Phase 2：读取 V2 规范 → 验证角色卡结构

读取 `e:\workplace\SillyTavern\src\validator\TavernCardValidator.js` 了解 V2 角色卡的必填字段结构。

### Phase 3：生成角色卡 JSON

基于用户的需求，生成完整的 V2 角色卡。

#### 3.1 示例对话编写（最重要的步骤）

**花最多时间在这上面。** 示例对话直接影响 AI 的角色扮演质量，比 system_prompt 里的指令强 100 倍。

编写原则：
- **数量**：3~5 段
- **覆盖范围**：日常闲聊、调情/互动、亲密场景（NSFW 角色必须要有性爱场景）
- **通过示例展示**：语气词（"嗯..."、"那个..."、"啊啦"）、句式（长句/短句）、口头禅、接话方式
- **NSFW 角色的示例对话必须包含**：前戏（亲吻/爱抚）→ 正戏（插入/体感）→ 高潮反应 → 事后温存

#### 3.2 NSFW 内容处理

如果用户要求 NSFW，你的 system_prompt 必须包含：

✅ **必写内容：**
- 详细的性爱描写要求（注重触感/温度/声音/气味/表情微变化）
- 敏感带列表（如脖颈、耳后、锁骨、大腿内侧、腰侧）
- 被动型角色的反应模式（用反应沟通而非语言，如点头、颤抖、呻吟）
- 中文写作要求
- **禁写清单**（必须包含）：非自愿/强迫、暴力、血腥、排泄类
- **重要规则**：不能替用户行动、不能替用户说话

✅ **personality 字段中必须包含：**
- 角色在性事中的整体表现（主动/被动/害羞/放荡）
- 身体的敏感度和特殊反应
- 高潮后的行为模式

✅ **示例对话中必须有明显的性爱场景示例**

#### 3.3 extensions 字段推荐值

```json
"extensions": {
  "talkativeness": 0.3,     // 被动型 0.25~0.35，普通 0.5，话痨 0.7+
  "fav": false,
  "world": "角色名的世界",
  "depth_prompt": {
    "prompt": "",
    "depth": 4,
    "role": "system"
  }
}
```

- **world** 的值必须与内嵌世界书和独立世界书的 `name` 字段一致
- 如果用户没有特殊要求，depth_prompt 保持空 `prompt` 即可

### Phase 4：生成世界书（Lorebook）

#### 4.1 什么是世界书？

**世界书是一套"关键词→触发→注入背景知识"的系统。**
- 平时不占用 prompt 长度（节省 token/上下文窗口）
- 当对话中提到某些关键词时，自动注入对应的背景知识
- 比如提到了"浴室" → 自动注入"角色的浴缸很小、她喜欢泡澡时听音乐"这段设定

#### 4.2 世界书条目字段详解

每条世界书条目的 JSON 结构：

```json
{
  "id": 0,                    // 唯一编号，从0开始
  "keys": ["关键词1", "关键词2"],  // 触发关键词（任意一个匹配就触发）
  "secondary_keys": [],       // 次级关键词（需要和主关键词同时匹配才触发）
  "comment": "",              // 给编辑者看的备注，AI 看不见
  "content": "触发的时注入的文字内容",  // ★ 条目内容
  "constant": false,          // 是否"始终注入"（设为true则不依赖关键词，一直注入）
  "selective": false,         // 是否"仅选择性触发"
  "insertion_order": 100,     // 注入顺序编号（越小越靠前）
  "enabled": true,            // 是否启用
  "position": "before_char",  // 注入位置：before_char（角色描述前）或 after_char（角色描述后）
  "use_regex": false,         // 关键词是否使用正则表达式匹配
  "extensions": {
    "depth": 4,               // 在对话历史的第几条消息处
    "probability": 100,       // 触发概率（0~100），100=总是触发
    "useProbability": false,  // 是否启用概率触发
    "selectiveLogic": 0,      // 匹配逻辑：0=主键，副键任意匹配 OR_ANY；1=主键+所有副键都匹配 AND_ALL
    "group": "",              // 分组名（同一组共享权重）
    "group_weight": 0,        // 组内权重
    "scan_depth": null,       // 往前扫描多少条消息
    "match_whole_words": false, // 是否必须全词匹配
    "case_sensitive": false,  // 是否大小写敏感
    "sticky": null,           // 触发后持续注入多少条消息
    "cooldown": null,         // 触发后冷却多少条消息
    "delay": null,            // 触发后延迟多少条消息才开始注入
    "role": 0,                // 用谁的角色注入：0=system, 1=user, 2=assistant
    "match_persona_description": false,     // 是否在 {{user}}人设描述 里搜索关键词
    "match_character_description": false,   // 是否在 角色description 里搜索关键词
    "match_character_personality": false,   // 是否在 角色personality 里搜索关键词
    "match_character_depth_prompt": false,  // 是否在 角色depth_prompt 里搜索关键词
    "match_scenario": false,               // 是否在 角色scenario 里搜索关键词
    "match_creator_notes": false           // 是否在 角色creator_notes 里搜索关键词
  }
}
```

#### 4.3 条目的两种类型（必须理解的区别）

| 特性 | `constant: true`（始终注入） | `selective: true`（选择性触发） |
|---|---|---|
| 触发条件 | 无条件，始终注入 | 仅在对话中提到 `keys` 关键词时才注入 |
| 适合放什么 | 角色的本质特征、核心设定 | 特定场景的深度设定、外貌、背景故事 |
| 优点 | AI 总是知道这个设定 | 节省 token，平时不占用上下文 |
| 缺点 | 持续占用 prompt 长度 | 对话中没提到关键词就不会触发 |

**推荐策略：**
- 核心设定（性格、说话方式）放在 `personality` 和 `mes_example`，不使用 constant 世界书
- 环境设定（家、工作场所）用 non-selective 但 non-constant → 用 insertion_order 控制
- 特定话题（过去经历、身体细节、性相关）用 selective，仅当话题出现时才触发
- 内衣/情趣/姿势等极端细节用 selective

#### 4.4 高级世界书技巧（主动推荐给用户）

> 用户不知道以下功能的，你要主动解释推荐：

1. **概率触发**：`probability` + `useProbability: true` — 给条目设一个触发概率（如 30%）。每次关键词触发时只有 30% 概率注入 → 让角色反应有随机性
2. **粘性**：`sticky: 5` — 条目触发后会在接下来的 5 条消息中一直注入，不怕关键词只出现一次
3. **冷却**：`cooldown: 3` — 触发后 3 条消息内不会再次触发，避免反复注入相同内容
4. **延迟**：`delay: 2` — 触发后等 2 条消息才注入，模拟"角色逐渐想起"的效果
5. **分组权重**：`group: "战斗反应"` + `group_weight: 10` — 同一组内的条目按权重竞争，只有权重最高的条目注入
6. **在角色描述中搜索**：`match_character_description: true` — 如果角色的 description 里有关键词，也算匹配，不用用户自己说
7. **深度控制**：`depth: 4` — 条目在对话历史的第 4 条消息处注入，而不是最开头
8. **正则匹配**：`use_regex: true` — `keys` 可以写正则表达式模式匹配

### Phase 5：生成用户人设（Persona）

#### 5.1 什么是用户人设？

在 SillyTavern 的术语中：
- **角色卡** = AI 扮演的角色（你的对话对象）
- **用户人设（Persona）** = 你自己（{{user}}）的定义

没有用户人设时，AI 对 {{user}} 一无所知。如果角色卡说"晚晴害羞地躲进你怀里"，AI 不知道能躲进什么样的怀里。有了用户人设，AI 就能：
- 描写 {{user}} 的外貌和反应
- 知道 {{user}} 的性格和说话方式
- 让角色卡的 `scenario` 和示例对话对 {{user}} 的设定保持一致

#### 5.2 人设文件格式

SillyTavern 的 Persona 管理使用 backup/restore 格式：

```json
{
  "personas": {
    "user_角色名.png": "你"
  },
  "persona_descriptions": {
    "user_角色名.png": {
      "description": "{{user}}的完整描述...",
      "position": 0,
      "depth": 4,
      "role": 0,
      "lorebook": "",
      "title": "角色关系"
    }
  },
  "default_persona": ""
}
```

字段说明：
- **`personas`** 的 key：头像文件名（不重要，只要不和其他人设重名就行）
- **`personas`** 的 value：人设名称（通常是"你"）
- **`description`**：{{user}} 的完整描述（外貌、性格、与角色的关系、互动风格）
- **`title`**：简短的关系标签，如"苏晚晴的男友"
- **`position`**：人设描述在 prompt 中的位置。0 = 在 main prompt 中插入，9 = 禁用
- **`depth`**：在 prompt 的第几条位置插入
- **`lorebook`**：人设是否关联世界书（通常不填）

#### 5.3 人设内容写法

用户人设的 `description` 应该包含：

```
{{user}}的名字由你自己设定，你是[角色]的[关系]。

【外貌】年龄、身高、体型、外貌特征描述...

【性格】性格特征、处事方式...

【与角色的关系】你们的关系状态、如何认识、相处模式...

【语言风格】语气特点、常用表达...

【性偏好（NSFW 角色用）】在床上风格、偏好、对待角色的方式...
```

**注意：** `description` 开头必须写 `{{user}}的名字由你自己设定`，因为用户可能在 SillyTavern 里改了用户名。

## AI 的 prompt 组装机制（帮助理解字段之间的关系）

SillyTavern 的 AI 收到 prompt 时，各个字段**按特定顺序拼接**。理解这个顺序有助于你决定内容放哪里：

```
1. system_prompt            ← 最开头的系统指令
2. Persona description      ← {{user}}的人设描述（如果 position=0）
3. character_book entries   ← constant=true 的世界书条目
4. description              ← 角色描述
5. personality              ← 角色性格
6. scenario                 ← 场景设定
7. mes_example              ← 示例对话
8. 聊天记录（从旧到新）
   ...
9. depth_prompt             ← 在指定深度重新注入
10. post_history_instructions ← 聊天历史最后的指令
```

**这意味着什么：**
- `description` / `personality` / `scenario` 彼此紧挨着 → 它们共同塑造角色的"本体认知"
- `system_prompt` 在全部之前 → 作为总体行为框架
- `mes_example` 在聊天记录之前 → AI 会把示例对话当作"历史"来学习
- `post_history_instructions` 在最后 → 影响"接下来怎么做"

## 常见问题（FAQ）—— 主动告诉用户

### Q1：NSFW 角色卡怎么处理？
- 在 `personality` 中写性事表现
- 在 `system_prompt` 中写性爱描写要求+禁写清单
- 在 `mes_example` 中包含性爱场景示例
- 在世界书中加入身体设定、内衣、体位等选择性条目

### Q2：如何让角色保持一致的说话风格？
- **示例对话是最有效的**——花最多时间写好 mes_example
- system_prompt 里写"始终保持温柔的语气"作为补充
- depth_prompt 可以在中段再次强调风格要求

### Q3：世界书条目太多会不会浪费 token？
- `selective: true` 的条目只在关键词出现时触发，平时不占 token
- `constant: true` 的条目永远占 token，少用
- `probability` 概率触发进一步节省 token

### Q4：用户人设必须生成吗？
- 不是必须的，但强烈推荐。没有用户人设时，AI 不了解 {{user}} 的形象，描写会变得笼统

### Q5：怎么导入？
1. 角色卡 → 导入角色 → 选 JSON 文件 → 弹窗问是否导入内嵌世界书 → 选是
2. 用户人设 → Persona Management → Restore → 选 JSON 文件
3. 独立世界书（可选）→ World Info → Import → 选 JSON 文件

## 设计原则总结

1. **用户是小白，主动介绍每项功能**
2. **示例对话 > 规则声明** — 花最多精力在 mes_example 上
3. **角色卡、世界书、用户人设三者的职责划分清晰**：
   - 角色卡：角色自身的一切（外貌、性格、说话方式）
   - 世界书：按需注入的深度设定
   - 用户人设：{{user}} 的形象
4. **NSFW 必须有禁写清单**：非自愿、暴力、血腥、排泄类内容不要写
5. **每生成一个字段，都简单解释一下这个字段是干什么的**，用户可能会说"哦那我要改一下"
